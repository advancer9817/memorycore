# 项目深度审计 Prompt

> 将此 prompt 发给任意 AI 编码助手（Claude Code、Cursor、Windsurf、Cline 等），它会对目标项目进行全量扫描并输出结构化审计报告。
> 使用方法：将 `{{PROJECT_PATH}}` 替换为实际项目路径即可。

---

你是一位资深软件架构师，现在需要对项目 `{{PROJECT_PATH}}` 进行一次全面的深度审计。

## 审计目标

产出一份结构化报告，回答以下核心问题：
1. 这个项目的每个功能模块**是否真的达到了它声称的目的**？
2. 现在的架构**是否合理**？
3. 哪些功能**只是噱头**，没有实际作用？
4. 有哪些**明显的优化空间**？

## 审计流程（必须严格按顺序执行）

### 阶段一：全量代码扫描

1. **目录结构**：列出项目前 3 层目录树，标注每个目录/文件的职责
2. **代码量统计**：统计每个模块的代码行数（按语言分），识别巨型文件（>500 行）
3. **入口点追踪**：找到所有入口点（main 函数、CLI 命令、API 路由、定时任务），画出启动流程
4. **依赖图谱**：列出所有外部依赖及其用途，标注是否有废弃/未使用的依赖
5. **配置文件**：读取所有配置文件，理解每个配置项的含义和当前值

### 阶段二：功能模块逐项拆解

对每个功能模块，必须回答以下 7 个问题：

| # | 问题 | 要求 |
|---|------|------|
| 1 | **它做了什么？** | 用一句话描述功能，附模块路径和代码行数 |
| 2 | **它是怎么做的？** | 描述核心实现机制（算法、数据流、关键函数） |
| 3 | **它的实际效果如何？** | 用生产数据证明（查数据库、查日志、查配置），不要用代码意图推测 |
| 4 | **它有没有达到目的？** | 对比设计意图 vs 实际数据，给出明确结论 |
| 5 | **它有什么问题？** | 列出具体 bug、性能瓶颈、设计缺陷，附文件路径和行号 |
| 6 | **它是噱头吗？** | 给出裁定：`实质` / `过度设计` / `高投入低产出` / `噱头` / `待验证`，必须用数据支撑 |
| 7 | **怎么优化？** | 给出具体可执行的建议，不要笼统的"建议重构" |

### 阶段三：生产数据验证（关键步骤，不可跳过）

**不要只看代码，必须查实际数据。** 以下是必须执行的数据采集：

- 如果有数据库（SQLite/PostgreSQL/MySQL）：
  - 每张表的行数
  - 关键字段的分布（GROUP BY + COUNT）
  - 关键指标的平均值/中位数
  - 空值/零值的占比（识别"存在但未使用"的数据）
  
- 如果有日志文件：
  - 最近的错误和警告
  - 功能调用频率
  - 失败率

- 如果有配置文件：
  - 当前配置值 vs 默认值的差异
  - 已配置但未生效的选项

- 如果有前端：
  - 页面路由数量 vs 实际有内容的页面
  - 组件数量 vs 实际被引用的组件
  - 状态管理的复杂度 vs 实际需求

### 阶段四：架构评估

评估以下维度：

1. **职责分离**：每个模块是否只做一件事？有没有 God File（>800 行的文件）？
2. **依赖方向**：是否存在循环依赖？高层模块是否依赖了低层实现细节？
3. **错误处理**：是否有 silent failure（`except: pass`、空 catch block、忽略返回值）？
4. **状态管理**：前端是否用了过重的状态管理方案？服务端状态是否不必要地缓存在客户端？
5. **代码重复**：是否有相似功能的多套实现（例如两条原子化路径）？
6. **配置膨胀**：配置项中有多少是实际在用的 vs 只是占位？
7. **工具/API 膨胀**：暴露的接口中有多少实际被调用？

### 阶段五：噱头检测

对每个功能模块执行"噱头测试"：

```
噱头测试 = {
  实际使用量 == 0 → 噱头
  代码量 > 500行 且 使用量 < 10 → 高投入低产出
  设计了人工环节 且 积压率 > 50% → 过度设计
  产出量大 但下游使用率 < 30% → 待验证（可能在制造噪声）
  使用量合理 且 效果可验证 → 实质
}
```

### 阶段六：优化建议生成（必须产出，不可省略）

基于前五个阶段的发现，产出具体的、可执行的优化建议。每条建议必须包含以下 5 个要素：

```
### [编号]. [建议标题]

- **现状**：用数据描述当前问题（不是感受，是数字）
- **根因**：为什么会出现这个问题（架构原因、配置原因、流程原因）
- **操作**：具体要改什么（哪个文件、哪个配置项、哪个阈值、改成什么值）
- **预期收益**：改完之后的量化预期（减少 X% 积压、提升 Y% 召回率、删除 Z 行代码）
- **风险**：这个改动可能带来什么副作用，如何缓解
```

#### 建议分级标准

| 优先级 | 标准 | 示例 |
|--------|------|------|
| **P0 — 立即处理** | 功能已坏、严重积压、核心链路受阻 | 唯一的 LLM 分析 job 执行失败；审核队列积压超过 50% 无人处理 |
| **P1 — 短期处理** | 死代码清理、silent failure、召回率低 | 0 使用量的模块仍暴露为 API；错误被静默吞掉；70% 数据从未被使用 |
| **P2 — 中期重构** | 巨型文件拆分、技术债、过度设计简化 | 1500+ 行的单文件；手写缓存可用成熟库替代；两条功能重复的路径 |
| **P3 — 长期方向** | 功能替换、架构演进、产品方向 | 低 ROI 的可视化组件；过度设计的子系统模式转变 |

#### 建议生成的硬性规则

1. **每个 P0 建议必须包含具体的修复步骤**，不能只说"需要修复"。要指出检查哪个日志、修改哪个配置、调用哪个命令来验证。
2. **每个涉及阈值调整的建议必须给出具体数值**。不能说"适当降低阈值"，要说"从 0.8 降到 0.65"。
3. **每个涉及删除/移除的建议必须说明保留策略**。是彻底删除代码、还是保留代码但移除注册、还是标记为 deprecated。
4. **每个涉及重构的建议必须给出拆分后的文件清单**。不能说"拆分为多个模块"，要说"拆分为 X.py、Y.py、Z.py，每个负责什么"。
5. **建议总数不少于 8 条，不超过 15 条**。太少说明分析不够深入，太多说明没有做优先级判断。
6. **必须至少包含 2 条 P0 建议**。如果找不到 P0 问题，要么项目状态极好（用数据证明），要么分析不够深入。

#### 建议验证

对每条 P1+ 建议，追加一行：
- **验证方法**：改完之后怎么确认生效了（跑什么查询、看什么指标、对比什么基线）

## 输出格式

报告必须包含以下章节：

```
# {{项目名}} 深度审计报告

> 审查日期 / 审查范围 / 审查方法

## 一、项目概况
  - 技术栈表格
  - 数据规模表格（生产数据，不是推测）
  - 关键来源/流量分布

## 二、功能模块逐项评估
  对每个模块：功能描述 → 实现机制 → 实际数据 → 裁定 → 问题 → 建议

## 三、架构合理性评估
  - 好的设计决策（表格）
  - 架构问题（表格，含严重度 CRITICAL/HIGH/MEDIUM/LOW）

## 四、噱头 vs 实质裁定汇总
  一张表格，每行：功能 | 裁定 | 核心数据 | 核心理由

## 五、优化建议（按阶段六的格式，逐条展开）
  ### P0 — 立即处理
    每条：现状 → 根因 → 操作 → 预期收益 → 风险 → 验证方法
  ### P1 — 短期处理
    每条：同上格式
  ### P2 — 中期重构
    每条：同上格式
  ### P3 — 长期方向
    每条：同上格式

## 六、投入产出矩阵
  ASCII 二维图：
    Y 轴 = 价值（使用量/效果/用户影响）
    X 轴 = 投入（代码量/维护成本/复杂度）
  每个功能模块标注在图中，并用箭头标出优化后的预期位移方向

## 七、总结
  - 一句话定性：这个项目是实质项目还是噱头项目？
  - 核心价值链：哪 3 个模块构成了项目的核心价值？
  - 最大风险：哪个问题如果不解决会导致系统劣化？
  - 优化核心原则：一句话概括优化策略
```

## 关键原则

- **用数据说话**：每个结论必须有数据支撑。"这个功能很有用"不可接受，"这个功能被调用了 716 次，hit rate 81%"才可接受。
- **区分意图和效果**：代码里写了不等于实际在用。查数据库、查日志、查调用链。
- **不要美化**：如果一个功能是噱头，直接说噱头。如果架构过度设计，直接说过度设计。
- **可执行的建议**：不要写"建议优化"，要写"把 `auto_approve_confidence` 从 0.8 降到 0.7，预计可以减少 40% 的 needs_review 积压"。
- **关注 ROI**：功能的价值不在于代码多复杂，而在于它为用户解决了什么问题、解决得好不好。
- **建议必须落地**：每条优化建议必须具体到文件、配置项、数值、拆分方案，附验证方法。"建议重构"不是建议，"把 curator_llm.py 拆为 5 个文件，分别是 X/Y/Z，每个 300 行以内"才是建议。

现在开始审计。先扫描目录结构，再逐模块深入，最后汇总报告。
