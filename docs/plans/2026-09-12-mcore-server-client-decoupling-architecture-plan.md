# mcore 服务端与客户端解耦架构演进与实施规划

> **创建日期**：2026-09-12  
> **状态**：方案决策与实施规划  
> **文档归属**：`/workspace/memorycore/docs/plans/`  
> **核心目标**：彻底解决跨机/远程连接 mcore 服务配置繁琐、各组件 Hook 与 Agent URL 到处修改的痛点，确立“服务端与客户端彻底解耦，所有请求统一打到本地客户端，客户端代理配置服务端 URL”的全新架构范式。

---

## 一、 架构演进背景与深层动因

### 1.1 现状与痛点剖析
目前 mcore 架构属于典型的“全功能单体服务”模式，MCP 服务端（FastMCP）、REST 业务接口、PostgreSQL 16 + pgvector 存储中枢以及各个 Agent（Claude Code、Hermes、Codex 等）的生命周期 Hook 脚本（`mcore-context.sh`、`mcore-ingest.py`）高度耦合在同一套运行环境中。

当用户在非服务端本地的远程工作站、笔记本或移动办公环境中使用各种 AI Agent 时，暴露出了严重的“多端配置熵增”与“环境裂化”问题：
1. **Agent 配置分散篡改**：每个 Agent 拥有独立的配置文件体系（Claude 的 `~/.claude/settings.json`、Hermes 的 `~/.hermes/config.yaml`、Codex 的 `~/.codex/config.toml`）。一旦服务端发生物理迁移、端口重映射或接入公网反代域名，必须逐一手工修改 5~6 处配置；
2. **Hook 物理路径强依赖**：生命周期 Hook 命令强行绑定了宿主机上的绝对路径（如 `bash /workspace/memorycore/scripts/hooks/...`），在未克隆完整源码仓库的轻量级客户机上根本无法运行；
3. **网络震荡与离线不可用**：移动办公时网络抖动或临时离线会导致远程调用直接抛错，缺乏客户端本地连接复用、离线缓存与异步重试队列机制；
4. **凭据弥散风险**：远程访问需要携带租户 API Key（`X-Tenant-Id` 与 `X-API-Key`），导致敏感凭据分散配置在各种 Agent 的明文设置中，不符合凭据收敛原则。

### 1.2 架构演进定调
用户明确指示：**“改一下架构，分为服务端与客户端，所有请求统一打到本地客户端上，客户端配置服务端 URL。”**

确立核心设计原则：
- **虚拟本地回环（Virtual Local Loopback）**：本地客户机上的所有 Agent 和 Hook 永远只与本地回环地址（`http://127.0.0.1:8318`）通信，彻底冻结所有上层 Agent 的配置；
- **配置单点收敛（Single Source of Configuration）**：整个客户端环境只存在一份统一的客户端配置文件（`~/.mcore/client.yaml`），负责维护上游服务端的 URL、租户标识与安全凭据；
- **能力边界严格划分**：
  - **服务端（mcore-server）**：专注数据面与控制面，包括 PostgreSQL 16 + pgvector 混合检索、多租户数据库隔离、模型提炼推演（LLM Ingest/Curator）、知识图谱拓扑及全局治理；
  - **客户端（mcore-client / Local Daemon）**：专注网络面与接入面，包括虚拟端口监听、协议自适应转发、凭据自动注入、连接池多路复用、离线上下文缓存及提炼回写持久化队列。

## 三、 技术实现方向与核心工程机制

依照用户严令，本章节确立纯工程架构、状态机、控制流与防御机制的技术实现方向，不输出大段具体业务代码。

### 3.1 客户端技术方向：极简自包含守护进程
1. **轻量级单体发布形态**：
   - 客户端必须是一个免复杂运行环境依赖的单文件执行体（原生二进制或无第三方重型依赖的脚本）；
   - 具备开箱即用的常驻守护能力（Windows 服务 / systemd user 服务 / 后台守护进程），随用户会话自动拉起。
2. **虚拟本地回环代理引擎**：
   - 默认接管本地 `127.0.0.1:8318` 端口；
   - 协议透明转发：拦截 `/mcp` 下的 JSON-RPC 请求，以及 `/api/v1/**` 下的 REST 与探针请求；
   - 协议自适应转换：客户端负责与远端服务端维护长连接（HTTP/2 或 HTTP Keep-Alive），向下兼容本地各类 Agent 的短连接、SSE 流式或 Chunked 传输。

### 3.2 单点配置中心与透明凭据注入机制
1. **客户端统一事实源规范**：
   - 配置文件固定在 `~/.mcore/client.yaml`；
   - 包含上游服务端配置（`server_url`）、租户隔离配置（`tenant_id`）、凭据鉴权配置（`api_key`）、连接池超时间隔与离线缓冲策略；
   - 支持通过轻量 CLI 单键切换环境（如 `mcore-client use cloud` 或 `mcore-client use local`）。
2. **透明安全注入网关**：
   - 本地 Agent 与 Hook 向 `127.0.0.1:8318` 发起请求时，无需在各处重复配置鉴权头；
   - 客户端在出站请求链路上，依据 `client.yaml` 自动注入：
     - `X-Tenant-Id: <tenant_id>`
     - `X-API-Key: <api_key>`
     - `X-Client-Version: <version>`
   - 彻底避免在多个 Agent 的明文配置文件中暴露企业或个人私有 API Key。

### 3.3 离线防护、本地缓存与写入可靠性保障 (WAL Queue)
1. **读路径（上下文召回）弹性降级**：
   - 客户端维护微型本地 LRU 缓存，最近召回的高频核心记忆在本地保留热备份；
   - 当检测到远端服务端不可达或网络严重抖动超时（> 2 秒）时，自动回落至本地缓存响应上下文，确保上层 Agent 对话流程不被外部网络卡死。
2. **写路径（会话记忆回写）WAL 事务日志队列**：
   - 当会话结束触发 `memory_ingest` 时，客户端首先以预写日志（Write-Ahead Log, WAL）方式将转录事件追加落盘至本地持久化队列；
   - 优先尝试实时上报至远端服务端；
   - 若上报失败或遇网络中断，客户端将该批次转录标记为 `pending`，由后台异步重试退避引擎在网络恢复后自动回放上报，做到**断网离线不丢记忆、网络恢复自愈补齐**。

### 3.4 原生内置 Hook 代理接口（消灭本地脚本路径硬编码）
1. **Hook 端点化下沉**：
   - 客户端直接内置暴露 `/api/v1/hooks/context` 与 `/api/v1/hooks/ingest` 两个标准的 HTTP 接口；
   - Claude Code、Hermes 等支持 HTTP 原生 Hook 的 Agent 直接通过 `{"type": "http", "url": "http://127.0.0.1:8318/api/v1/hooks/..."}` 接入；
   - 彻底消除在客户端机器上寻找 Bash、Python 或代码仓库物理路径的宿命缺陷。
2. **经典脚本兼容层**：
   - 客户端安装程序将兼容版极简脚本统一分发至系统标准 PATH（如 `~/.local/bin/` 或 `~/.mcore/bin/`）；
   - 脚本内部仅有单行指令向本地客户端发起请求，完全剥离所有复杂的业务逻辑与端点判断。

## 四、 阶段演进实施规划 (Phase Roadmap)

### Phase 1：客户端单点配置中心与轻量代理核心（先行）
- **目标**：落地 `~/.mcore/client.yaml` 规范，实现本地 `:8318` 虚拟透明转发服务与请求头自动注入；
- **实施要点**：
  1. 制定 `client.yaml` 结构定义（支持多环境 profile 切换：local, cloud, home_server）；
  2. 实现基于轻量 HTTP 服务器的本地反向代理，接管 `/mcp` 与基础探针接口；
  3. 实现出站 HTTP 拦截器：统一附加 `X-Tenant-Id`、`X-API-Key` 与 `User-Agent`。

### Phase 2：一键配置 CLI 与多 Agent 自动接管
- **目标**：实现 `mcore-client` 命令行工具，提供一键初始化与一键切环境能力；
- **实施要点**：
  1. CLI 实现 `mcore-client init`、`mcore-client status`、`mcore-client switch <env>`；
  2. 重构 `connect_agents.py`：所有 Agent 的 MCP 服务与 Hook 配置统一收敛指向 `127.0.0.1:8318` 本地客户端；
  3. 提供多操作系统（Linux / macOS / Windows）的标准服务托管模板。

### Phase 3：内置 HTTP Hook 端点与离线重放队列
- **目标**：彻底摆脱客户端机器对源码仓库与复杂本地脚本的依赖；
- **实施要点**：
  1. 客户端内置实现原生 HTTP Hook 处理引擎（直接解析 Claude Code / Hermes 标准 Payload）；
  2. 建立本地 WAL 磁盘队列目录（`~/.mcore/queue/`），实现网络故障时的离线暂存与重试状态机；
  3. 客户端实现健康打分与连接状态聚合输出（`GET /health` 同时反馈本地客户端与远端服务端的健康状况）。

### Phase 4：服务端适配与生产割接验证
- **目标**：服务端配置收敛，完成远程工作站到云端 mcore 全链路实证；
- **实施要点**：
  1. 验证服务端多租户与 API Key 鉴权拦截器无缝识别客户端出站标头；
  2. 全链路集成验证：在独立全新远程机器上，仅安装客户端单执行体，验证 Claude Code 与 Hermes 的上下文自动注入与会话结束自动回写；
  3. 更新官方仓库文档及迭代日志。

## 五、 预期收益与风险防范

### 5.1 架构预期收益
1. **零改动终极体验**：无论服务端迁往何处，5 大 Agent 永远只需连接 `127.0.0.1:8318`，换环境只需 `mcore-client switch` 一秒切完；
2. **跨平台纯净解耦**：远程开发机不需要 clone 数百兆的 mcore 源码仓库，无需本地 PostgreSQL，仅需几兆的轻量客户端；
3. **企业级安全合规**：凭据由本地客户端统一托管，杜绝散落明文泄露风险；
4. **工业级高可用**：本地 WAL 队列彻底消灭因网络短时闪断导致的记忆丢失。

### 5.2 风险防范对策
- **端口冲突防范**：当在运行服务端的宿主机上同时跑客户端时，提供回环直连旁路（Direct Passthrough）模式，或支持参数化端口回落；
- **本地队列容量控制**：设置本地暂存上限（默认最大 100MB / 1000 条），超限时执行 LRU 预警并记录审计日志；
- **跨平台网络权限**：Windows 端提示放行回环防火墙权限，避免第三方安全软件误杀守护进程。
