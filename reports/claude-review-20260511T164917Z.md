## Code Review: local-memory-mcp v0

---

### CRITICAL

**C1 — `list_recent` silently caps at 100, breaking curator for any DB > 100 records**
`local_memory_mcp.py:423`
```python
rows = conn.execute("SELECT * FROM memories ORDER BY updated_at DESC LIMIT ?",
    (max(1, min(int(limit), 100)),)  # hard cap at 100
```
`curator_report` calls `list_recent(limit)` at line 595 with `limit=500` (the default). The cap means the curator never sees more than 100 records regardless of what the caller requests. Stale/archive/duplicate detection silently degrades on any non-trivial DB.

Fix: remove the cap from `list_recent` or add a separate `_list_recent_uncapped` for internal use. The 100-cap belongs only on the MCP-exposed `memory_list_recent` tool.

---

**C2 — Connection never explicitly closed; relies on CPython GC**
`local_memory_mcp.py:76-86, 266, 339, 397, …`

`sqlite3.Connection.__exit__` commits/rolls back the transaction but does **not** close the connection. In CPython, reference counting closes it when `conn` goes out of scope, but this is an implementation detail. In PyPy or any context where the reference lingers (e.g., a `Row` object holding a reference), the connection stays open. In the MCP server process, which is long-lived, this pattern accumulates open file descriptors.

Fix:
```python
from contextlib import contextmanager

@contextmanager
def get_conn():
    conn = _open_conn()
    try:
        yield conn
        conn.commit()
    except:
        conn.rollback()
        raise
    finally:
        conn.close()
```
Replace all `with connect() as conn:` with `with get_conn() as conn:`.

### HIGH

**H1 — `enable_load_extension` never disabled after sqlite_vec load**
`local_memory_mcp.py:83-84`
```python
conn.enable_load_extension(True)
sqlite_vec.load(conn)
# never disabled
```
Any SQL reachable after this point can load arbitrary shared libraries via `SELECT load_extension(...)`. For a local tool the blast radius is limited, but any FTS query that accepts user-controlled input runs on a connection with extension loading open.

Fix: `conn.enable_load_extension(False)` immediately after `sqlite_vec.load(conn)`.

---

**H2 — `init_db` runs on every `connect()` call**
`local_memory_mcp.py:85`

Every single DB operation calls `connect()` → `init_db()`. `init_db` runs a full `executescript` (multiple DDL statements) plus a `SELECT COUNT(*) FROM memories_fts WHERE id IS NULL` on every call. For a server process handling many tool calls, this is significant overhead.

Fix: use a module-level flag or a `threading.Event` to run `init_db` once per process:
```python
_db_initialized = False

def connect() -> sqlite3.Connection:
    global _db_initialized
    conn = _open_conn()
    if not _db_initialized:
        init_db(conn)
        _db_initialized = True
    return conn
```

**H3 — `semantic_search` calls `semantic_index` on every invocation**
`local_memory_mcp.py:513`
```python
def semantic_search(query: str, limit: int = 10, status: str = "active") -> list[dict[str, Any]]:
    if not semantic_available():
        return []
    semantic_index(limit=1000, force=False)   # ← full index pass on every search
```
`semantic_index` opens a new connection, queries for unindexed records, and potentially embeds up to 1000 records. This makes every `memory_semantic_search` MCP call O(n) before the actual search begins.

Fix: call `semantic_index` only from `memory_semantic_index` (explicit) and from a background/scheduled path. Remove the implicit call from `semantic_search`.

**H4 — FTS falls back to raw user query when tokenizer finds no terms**
`local_memory_mcp.py:318-319`
```python
terms = re.findall(r"[\w\u4e00-\u9fff]+", query, flags=re.UNICODE)
fts_query = " OR ".join(terms) if terms else query   # ← raw query on empty terms
```
If `query` is all punctuation (e.g., `"--"`, `"NOT"`, `"NEAR/3"`), `terms` is empty and the raw string is passed to `MATCH`. FTS5 will raise `sqlite3.OperationalError` on malformed queries, crashing the search call entirely. The caller gets an unhandled exception rather than an empty result.

Fix:
```python
fts_query = " OR ".join(terms) if terms else None
if fts_query:
    base += " JOIN memories_fts f ON f.id = m.id"
    clauses.append("memories_fts MATCH ?")
    params.append(fts_query)
```

**H5 — `executescript` auto-commits any open transaction**
`local_memory_mcp.py:90, 159, 188`

Python's `sqlite3.executescript` issues an implicit `COMMIT` before running the script. If `init_db` is ever called inside an open transaction (e.g., during the FTS rebuild path at line 159), the partial transaction is silently committed. The FTS rebuild at lines 159-186 drops triggers, drops the FTS table, recreates them, and re-inserts rows — all via `executescript`. If the process crashes between the DROP and the re-INSERT, the FTS table is empty and triggers are gone.

Fix: the FTS rebuild should use explicit `BEGIN`/`COMMIT` with individual `execute()` calls, not `executescript`.

### MEDIUM

**M1 — `consolidate()` ignores `dry_run=False`; MCP tool is a silent no-op**
`local_memory_mcp.py:552-561`
```python
def consolidate(dry_run: bool = True, limit: int = 50) -> dict[str, Any]:
    # v0 heuristic: ... No destructive action unless future version.
    ...
    return {"dry_run": dry_run, "duplicate_title_groups": duplicates, ...}
```
The `dry_run` parameter is accepted and echoed back but never checked. `memory_consolidate(dry_run=False)` does nothing different from `dry_run=True`. The MCP tool contract is broken. Either remove the parameter and document the function as always dry-run, or implement the apply path.

**M2 — `feedback score` has no range validation**
`local_memory_mcp.py:405`

`score: float` is accepted and stored without bounds checking. A caller passing `score=1e308` or `score=float('inf')` will store that value, corrupting `feedback_score` on the parent memory. The `AVG()` aggregate will then return `inf`, which propagates to all subsequent reads.

Fix: `score = max(-10.0, min(10.0, float(score)))` or document and enforce a `[-1.0, 1.0]` contract.

**M3 — `run_curator.sh`: any non-empty `LOCAL_MEMORY_CURATOR_APPLY` triggers `--apply`**
`run_curator.sh:14`
```bash
${LOCAL_MEMORY_CURATOR_APPLY:+--apply}
```
Setting `LOCAL_MEMORY_CURATOR_APPLY=false` or `LOCAL_MEMORY_CURATOR_APPLY=0` still passes `--apply` and mutates the DB. This is a footgun for ops scripts that set env vars to explicit false values.

Fix: check the value explicitly:
```bash
[[ "${LOCAL_MEMORY_CURATOR_APPLY:-}" == "1" ]] && APPLY_FLAG="--apply" || APPLY_FLAG=""
"$PY" "$SERVER" curator ... $APPLY_FLAG > "$REPORT"
```

**M4 — `probe_mcp.py` writes test records into the production DB with no cleanup**
`probe_mcp.py:18`
```python
add = await session.call_tool('memory_add', {
    'type':'timeline_event',
    'title':'local-memory-mcp protocol probe',
    ...
})
```
Every probe run inserts a permanent record into the live DB. There is no teardown. Over time this pollutes the memory store with probe artifacts that affect curator scoring and context packs.

Fix: either point the probe at a temp DB (`LOCAL_MEMORY_DB=/tmp/probe-test.sqlite3`), or add a cleanup step that deletes records with `tags=['probe']` after the test.

**M5 — CLI `context` subcommand silently drops `project_path`**
`local_memory_mcp.py:924`
```python
print(build_context_pack(args.task, args.agent, scope=args.scope, token_budget=args.budget)["context"])
```
`build_context_pack` signature is `(task, agent, project_path, scope, token_budget)`. The CLI passes `project_path` positionally as the third argument — but here it's omitted, so `scope` lands in the `project_path` slot and `token_budget` lands in `scope`. The context pack will always have wrong scope/project_path from the CLI.

Fix:
```python
build_context_pack(args.task, args.agent, project_path="", scope=args.scope, token_budget=args.budget)
```
And add `--project-path` to the `context` subparser.

**M6 — `update_status` silently no-ops on unknown ID**
`local_memory_mcp.py:397-401`
```python
conn.execute("UPDATE memories SET status=?, updated_at=? WHERE id=?", (status, now(), memory_id))
row = conn.execute("SELECT * FROM memories WHERE id=?", (memory_id,)).fetchone()
# row is None if id didn't exist; error raised after with-block exits
```
The UPDATE runs without checking `rowcount`. The error is raised after the context manager exits (after commit), so the no-op UPDATE is committed. The error message is correct, but the caller cannot distinguish "not found" from a DB error. Use `conn.execute(...).rowcount` to detect the miss before committing.

**M7 — HTML export: `data_json` `</` replacement is applied to the entire serialized payload including keys**
`local_memory_mcp.py:804`
```python
data_json = json.dumps(payload, ensure_ascii=False).replace("</", "<\\/")
```
`<\/` is valid in JSON string values but not in JSON keys. If any memory content or title contains `</` as part of a key name (unlikely but possible via `metadata_json`), the replacement corrupts the JSON. More practically, `ensure_ascii=False` combined with no HTML-entity encoding means a memory whose `content` contains `<!--` could interact with the HTML parser in older browsers.

Safer approach: use `ensure_ascii=True` for the embedded JSON blob, or apply the replacement only to string values via a custom encoder.

### LOW

**L1 — Hardcoded `/home/advancer/` paths in four places**
`local_memory_mcp.py:34, 912`; `run_curator.sh:3`; `probe_mcp.py:6`

These break for any other user or deployment path. `DEFAULT_DB` at line 34 is evaluated at import time, so even if `LOCAL_MEMORY_DB` is set, the fallback is wrong for other users.

DEFAULT_DB = Path(os.environ.get(

**L2 — `db_path()` calls `mkdir` on every invocation**
`local_memory_mcp.py:72`

`db_path()` is called by `connect()` which is called by every operation. `mkdir(parents=True, exist_ok=True)` is a syscall on every DB access. Cache the result or call `mkdir` once at startup.

**L3 — `source_agent` default inconsistency**
`local_memory_mcp.py:250, 405, 737` vs schema default at line 100

MCP tool defaults use `"hermes"` as `source_agent`; the DB schema default is `"unknown"`. Records added via direct Python calls (not MCP) get `"unknown"`, while MCP calls get `"hermes"` even when called by a different agent. The field loses meaning.

Fix: remove the default from the MCP tool signatures and require callers to pass it explicitly, or default to `"unknown"` everywhere.
